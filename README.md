# 📖 Introduction

This Template goal is to provide a setup with React Native + Expo Bare Workflow, meaning that you can use all Expo Libraries and No-Expo Libraries easily, with everything you need to integrate EAS Cloud Services: OTA Updates, easy app building and distribution to the stores. Yes, you can build and submit iOS Apps from a Linux or Windows PC! 😁

<br/>
<br/>

# 🚀 Getting Started

1. Change **App Name** and **Slug** in `app.json`
2. Change your **Android Package** name and **iOS Bundle Identifier** in `app.json`.

<br/>
<br/>

# 🗂️ Folder Structure

In the `root` folder you will find a folder called `src`, with other empty folders inside of it. <br/>
This is a sugestion on how to organize your app files. We **strongly** recommend you to follow that folders structure.

⚠ **NOTE:** Feel free to create other folders as your project grows and evolves.

# 🔗 EAS Integration

You will need to install the `eas-cli` to use all EAS Services. To do so, run:

```
$ npm install -g eas-cli
```

⚠ **NOTE:** Expo Docs recommend using `npm` instead of `yarn` to install global packages.

<br/>
<br/>

## ➡🚪 Log in to Fetchly Expo Account

You will need to log in your **cli** to **Fetcly's Expo Account**. To do so, run:

```
$ eas login
```

And follow the instructions on your terminal.

⚠ **NOTE:** If you are not sure about the credentials to use, please reach out the **DevOps** Team, they can help you with that.

---

You can check if your **cli** is correctly loged in by running:

```
$ eas whoami
```

<br/>

## ⚙️ Configure the project

Now, we need to configure both **Android** and **iOS** projects. Run:

## 🛠️ Build, publish and update your app

To understand how EAS Build/Submit/Update works, you can refer to [this page](https://docs.expo.dev/eas-update/how-eas-update-works/) on their official docs.

In this template, we use **3** main profiles: `preview`, `staging` and `production`.

<br/>

### 📝 Profiles

`preview`: This profile is intended to be installed on real devices by your team and other stakeholders, to test out the app in production-like circumstances but in a Developer Environment. This build **can not** be submitted to app stores but can be updated with EAS Update using the `preview` channel.

⚠ **NOTE:** [Here](https://docs.expo.dev/build/internal-distribution/#install-and-run-the-build) you can find instructions on how to install the build generated by the `preview` profile.

<br/>

`staging`: This generates a build ready to be submitted to the app stores, but will not be shipped to production. This will be under Internal Testing on Google Console and should be kept on TestFlight only on Apple Store Connect. This build can be updated with EAS Update using the `staging` channel.
This will also increment the `buildNumber` for iOS and `versionCode` for Android. The `version` value needs to be manually updated on `app.json` BEFORE running the command. The CLI will prompt you to commit the changes so it persists over the nexts builds. See Limitations in the end of this file for more information

<br/>

`production`: This generates a build ready to production and on submit, it will be shipped to production in Google Play Console. This will also be under the TestFlight in App Store Connect as this is the Apple flow, but this CAN be shipped to production. This build can be updated with EAS Update using the `production` channel.

<br/>
<br/>

### ⚙️ Building your app

We have set a few scripts on `package.json` that wraps the `eas` commands and the flags you’ll need for each profile. Follow the CLI prompt until it’s finished.<br/>
The first time you’re building you app (in `preview` profiles and above) a few things will happen:<br/>

1. For `Android` it will prompt you to **Generate a new Android Keystore**. hit **`Y`**.
2. For `iOS` it will prompt you to **Log in to your Apple Account**. It is strongly recommended that you do. Ask your PM for help on the **Fetchly's Apple Connect Credentials**.

<br/>

`yarn build-preview`:
Generate the preview build that can be installed through a link that will be provided once the build is finished. NOT production ready and should be used by the developer team and other stakeholders as an evaluation version.

<br/>

`yarn build-staging`
This generates a build ready to be submitted to an app store for internal testing. Follow the CLI steps and when it prompts you to commit the changes, it’s highly recommended that you do it so the version upgrade persists over the nexts builds.

<br/>

`yarn build-prod`
This generates a build ready to be submitted to an app store, for release to the general public or as part of a store-facilitated testing process such as TestFlight.
This will also increment the `buildNumber` for iOS and `versionCode` for Android. The `version` value needs to be manually updated on `app.json` BEFORE running the command. The CLI will prompt you to commit the changes so it persists over the nexts builds. See Limitations in the end of this file for more information

<br/>
<br/>

### 🚀 Submitting Successful Builds

Here is were we will publish our apps to the stores, both for production and internal testing.
The first time you’re submitting you app, you will probably need to **setup credentials for both stores**. The CLI prompts and provides all information you need and how to do it, with links to tutorials on how to generate the keys and all you'll need.

We have two profiles to submit the apps to the stores. `staging`, that publishes the builds in internal testing and `prod`, that goes to production and make it available to the public.

<br/>

`yarn submit-staging`
This is how you ou can ship your successful production builds to Apple and Google app stores. Follow the steps in the CLI. When prompted `What would you like to submit?` choose `Select a build from EAS` and then select the latest successful production build. After it’s finished, you should be able to see your app on **App Store Connect TestFlight** and **Google Play Internal Testing**.

<br/>

`yarn submit-prod`
This is how you ou can ship your successful production builds to Apple and Google app stores. Follow the steps in the CLI. When prompted `What would you like to submit?` choose `Select a build from EAS` and then select the latest successful production build. After it’s finished, you should be able to see your app on App Store Connect and Google Play console.

⚠ **NOTE:** Find more details on the submit process for [Android](https://docs.expo.dev/submit/android/) and [iOS](https://docs.expo.dev/submit/ios/).

<br/>
<br/>

### 🦄 Alternative: Automatically Submitting a Successful Build

As an alternative to make this process faster, there are two scripts that will automatically submit the successful build to its respective store. They follow the same principles and rules described in the previous sections, so we won’t cover them again.
<br>
The scripts are:

`build-submit-staging`

`build-submit-prod`

We build the scripts this way to allow the developer to choose a more controlled or faster process.

<br/>
<br/>

### 🧙‍♂️ OTA Updates

Each profile described in the above sections creates a respective update channel that will be use to deliver OTA updates to the build that is linked to that channel. The linking process between a channel and its build is automatically handled because they are using the same names (preview, staging and production). All you need to do is run the scripts and the linked build will be updated.

⚠ **NOTE:** Expo Docs says that it should take a few minutes to the updates be reflected in the app.
You may need to force close and run the app again twice before the changes show on your build.

`yarn update-preview`

`yarn update-staging`

`yarn update-prod`

## ⛔️ Limitations

We are using the Local version management with autoIncrement option set to true on production build, as recommended by the Expo docs. Even this is the recommended workflow, it has some limitations:

- With `autoIncrement`, you need to commit your changes on every build if you want the version change to persist. This can be difficult to coordinate when building on CI.
- `autoIncrement` is not supported if you are using a dynamic config (app.config.js).
- For bare React Native projects with Gradle configuration that supports multiple flavors, EAS CLI is not able to read or modify the version, so `autoIncrement` option is not supported and versions will not be listed in the build details page on [expo.dev](https://expo.dev/).

## 🤯 Troubleshooting

If you find any issues while building your apps using EAS, you might need to add custom `infrastructure` or `platform` related configuration on your `eas.json` file. <br/>
You can refer to the oficial docs on [this page](https://docs.expo.dev/build-reference/infrastructure/) for more information about `infrastructure` (if you need an specific OS to run your build, such as MacOS Monterey for example).<br/>
You can refer to the [Android](https://docs.expo.dev/build-reference/android-builds/) or [iOS](https://docs.expo.dev/build-reference/ios-builds/) for more detailed information on each `platform` builds configuration.

Example of a custom `eas.json` config:

```
{
    ...other root configs
        "build": {
                "preview": {
                "node": "16.14.0",
                "yarn": "1.22.19",
                "distribution": "internal",
                "ios": {
                    "image": "macos-monterey-12.4-xcode-13.4"
                },
                "channel": "preview"
            },
            ...other profile configs
        }
}
```
